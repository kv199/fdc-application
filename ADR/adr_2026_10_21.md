# ADR 2026-10-21: Shift Lab recording

## Record raw Data Out packets in a separate database

**Status:** Accepted.

### Context
- Shift Light limiter and cue logic was fixed four times in a row, and each fix was checked only against invented numbers in tests.
- `fdc.sqlite` keeps only the bounded result of Shift Light learning, and Driver Analysis recordings do not store engine power, so there was no real drive to replay the learner against.
- Recorded drives must not change Shift Light behavior, its persistence contract, or the size and migration safety of `fdc.sqlite`.

### Decision
- The native Direct Data Out receiver stores every accepted 324-byte packet whose `IsRaceOn` is `1`, unchanged, in `fdc-lab.sqlite` next to `fdc.sqlite` in the application-data directory.
- Recording is always on in this prototype and has no user interface. It uses a bounded channel and its own writer thread, so a slow or failing write drops packets instead of delaying the HUD.
- Packets are grouped into sessions by car identity and by gaps longer than two seconds; the database is limited to 200 MB, and the oldest sessions are deleted first.
- `fdc-lab.sqlite` uses the default rollback journal, so the file is complete after every commit.
- The development tool `tools/shift-lab.mjs` replays a copy of the file through the same Shift Light bundle, compares the result with a copy of `fdc.sqlite`, and reports an independent power-curve and gear-ratio reference. It writes nothing.
- Recording fixtures for regression tests stay on the developer's computer and out of Git; tests that need them are skipped without them.

### Consequences
- `fdc-lab.sqlite` is the one exception to feature persistence living in `fdc.sqlite`; it holds raw telemetry only and no feature state.
- No new telemetry transport, port, or runtime dependency is added, and Shift Light learning is unchanged.
- The last roughly one hour of driving is kept on disk, including map positions; the file never leaves the computer unless the user copies it.
- CI cannot run recording-based regression tests.

## Derive Shift Light points from the power curve and gear ratios

**Status:** Accepted.

### Context
- Shift Light learned a shift point only at the RPM where the driver had shifted, and never moved below it. A Shift Lab recording of a stock Skyline GT-R settled on 8,783-8,992 RPM while its power curve and gear ratios put the best points at about 7,500 and 7,050 RPM.
- The simplified model of September 2026 deliberately did not reconstruct an engine or gearbox model, because the earlier model rejected normal shifts and was hard to maintain.
- The `boost` field of Data Out stays almost constant while driving, so it cannot show a turbo lag after a shift.

### Decision
- The learner builds a power curve from settled full-throttle frames, including wheelspin, and gear ratios from frames without wheelspin, in memory for each run.
- For each gear pair it computes the first RPM from the power peak where the next gear has at least as much power, or the limiter when there is none, and uses it only with enough curve coverage and a known limiter.
- Real comparable shifts verify that point; when contradictions outnumber agreements and there are at least two, the pair falls back to the existing learning.
- The model point outranks an OPTIMAL target and is persisted as a nullable `model_rpm` on the gear target, an additive schema change; the curve and ratios are not persisted.
- The Shift Light tab shows only the gear pair, the shift point, and READY or LEARNING; model details stay in diagnostics and the Shift Lab report.

### Consequences
- A car whose power falls before the limiter gets its shift points from a few full-throttle runs instead of never.
- After a restart, the persisted point stays in use until a new run produces a fresh one.
- A turbo lag after a shift is caught only through contradicting real comparisons, not predicted.
