# Architectural Decision Records — 2026-08-11

## 09:53 - Use a develop-first workflow and named build channels

### Context
- Day-to-day HUD tasks should remain lightweight, while stable gaming builds need a clear promotion point.
- Cargo's built-in `debug` and `release` directories describe compiler profiles, not the Git branches that produced them.

### Decision
- Perform normal work and focused commits directly on `develop`; create feature branches only after explicitly agreeing that a change is large, risky, or long-running.
- Merge accumulated work into `main` only after Kirill accepts it and requests promotion.
- Add a release-derived Cargo profile named `develop` for testable executables from the `develop` branch, while keeping the standard `release` profile for stable executables built from `main`.
- Reserve Cargo's standard `debug` profile for technical diagnostics.

### Consequences
- Development builds are stored under `src-tauri/target/develop`, and stable builds remain under `src-tauri/target/release`.
- Development builds stay optimized enough for realistic game testing but rebuild faster and retain limited debug information.
- Build-channel correctness depends on confirming the checked-out Git branch before producing an executable.

## 12:39 - Synchronize remote branches as part of a release

### Context
- Local promotion to `main` and local executable builds are not enough to keep the remote repository aligned with the gaming release.
- A release can appear complete locally while `origin/develop` or `origin/main` still lacks the commits used to produce the build.

### Decision
- After an explicitly approved promotion, successful validation, and a successful `main` release build, push both `develop` and `main` to `origin`.
- Treat a failed push as an incomplete release and report it instead of claiming the release is fully synchronized.
- Do not push feature branches as part of the normal release workflow unless explicitly requested.

### Consequences
- Every accepted release has its source history available on the remote branches that represent development and production.
- Release completion now includes remote synchronization in addition to merge and build validation.
